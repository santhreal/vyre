# Vyre long-term goal

**1. End state.** Build one workload-neutral compiler and runtime: typed source or API input → validated `Program`/`ProgramGraph` → canonical IR optimization → target-neutral megakernel artifact → measured backend selection → concrete lowering → static or persistent execution → verified outputs and evidence. Every capability must serve multiple workloads. External model kernels may appear only as independent benchmark harnesses and correctness oracles. Vyre must contain no model-specific crate, module, API, tensor namespace, checkpoint manifest, topology, tokenizer, chat template, or specialized kernel for any external product.

**2. Canonical execution plan.** Active work lives only in the maintainer's local `BACKLOG.md`. Every row contains a unique ID, exact affected files and symbols, one observed defect or missing capability, the required architectural change, measurable acceptance criteria, relevant correctness and performance gates, and the deduplication boundary. Cover every workspace crate and every review vector: organization, architecture, deduplication, utilization, wiring, correctness, robustness, capability, innovation, speed, testing, documentation, packaging, release, C API, C++ API, and operator execution. Reject generated variants, “resolve finding” labels, documentation-only substitutes, string-presence tests, and unfinished stubs presented as shipped work.

**3. `vyre-megakernel` compiler boundary.** The publishable `vyre-megakernel` workspace member owns target-neutral whole-graph compilation declared by `docs/CRATE_OWNERSHIP.toml`. Inputs: validated typed `ProgramGraph`, immutable external facts, exact symbolic bindings and constant identities, and an explicit bounded `SearchBudget`. Outputs: a versioned canonical `Artifact` containing dependency nodes and typed data/retained/materialization edges, a compiler-selected plan, canonical ABI, resource liveness, geometry, provenance, and stable digests; plus optional target-specific `TargetPayload` attachments inside an `ArtifactEnvelope`. Artifact identity never includes runtime retention or admission policy.

**4. Foundation IR and optimizer.** `vyre-foundation` is the single semantic authority for types, shapes, access, lifetimes, aliases, state generations, effects, algebraic laws, canonical bytes, graph analysis, and optimization facts. Layer 1 passes live in `vyre-foundation/src/optimizer/` (canonicalization, constant propagation, dead-value and dead-region removal, CSE, exact division/remainder rewrites, range and overflow proofs, loop unrolling, vectorization and tiling annotations, layout propagation, dtype legalization, fusion discovery, liveness, buffer reuse, allocation planning, and related compile-time analysis).

**5. Primitive and library completeness.** Audit `vyre-primitives/src`, `vyre-intrinsics/src`, `vyre-libs/src`, `docs/optimization/OP_MATRIX.toml`, and lego-audit surfaces so there is one implementation per semantic operation. Tier 2.5 primitives own reusable substrate loops and reductions. Category A in `vyre-libs` owns pure backend-neutral compositions with zero dedicated lowering. Category B remains explicitly observable or implementation-defined. Category C in intrinsic crates owns only hardware-dependent contracts with deterministic reference fixtures and explicit backend lowering. Keep neural, scan, math, graph, and parser compositions generic rather than product-shaped.

**6. Driver consolidation and honest routing.** `vyre-driver` owns one backend-neutral contract for capabilities, compilation, binding, launch plans, artifact caches, allocation, residency, timing, readback, routing inputs, and result evidence. Concrete drivers keep only substrate-specific work: CUDA device probing and PTX paths in `vyre-driver-cuda`; adapter/device, Naga/WGSL, bind groups, and pipelines in `vyre-driver-wgpu`; SPIR-V emit in `vyre-driver-spirv`; Metal on Apple targets. Remove overlapping planner types, compatibility aliases, per-driver cache identities, duplicated binding validation, duplicated shape logic, and shared-crate backend strings.

**7. Runtime and persistent megakernel.** `vyre-runtime` consumes canonical megakernel artifacts and owns resident control, ring, debug, IO, program, immutable-weight, scratch, output, and per-sequence state resources; bounded admission and accounting; cold/warm lifecycle; sequence start/reset/cancel/finish; generation-checked state; tenant fairness and priority; backpressure; cancellation; timeout; replay; fault containment; telemetry; and cleanup. Target-neutral compilation and selection belong in `vyre-megakernel`, not a runtime bytecode interpreter. Static fused and persistent routes must consume the same artifact class and produce identical bytes and state transitions for equivalent inputs.

**8. Repository organization and deduplication.** Enforce one owner and one dependency direction for every responsibility using `docs/CRATE_OWNERSHIP.toml`, `docs/optimization/OWNERSHIP.toml`, `docs/optimization/OP_MATRIX.toml`, and architecture gates. Consolidate duplicate planners, emitters, parsers, wire formats, fingerprint functions, tensor contracts, graph forms, state schemas, cache keys, capability records, routing selectors, allocation utilities, test harnesses, fixtures, constants, CLI schemas, and documentation sources. Remove thin wrapper crates, consumer-specific aliases, compatibility reexports, dead routes, orphan tests, unused public symbols, and generated source copies after every caller migrates.

**9. Performance, research, and innovation.** Measure before and after with `vyre-bench`, `BENCH_TARGETS.toml`, raw device timestamps, wall time, allocation counts, memory traffic, occupancy, launch geometry, cache state, host/device metadata, compiler identity, and exact output parity. Build generic benchmark matrices for scans, regex, parsers, graph analytics, dense/sparse math, attention, recurrent updates, quantization, compiler throughput, cold compile, warm replay, static fusion, persistent execution, multi-tenant latency, and external full-workload harnesses. Beat best available native baselines rather than naive loops. Research ledger rows for external model kernels stay `release_floor_eligible = false` with empty `vx_rows` when they are consumer-specific or documentation-only.

**10. Completion and prohibitions.** Complete only when audited backlog rows are implemented or directly proven obsolete; affected APIs, callers, tests, docs, matrices, benchmarks, artifacts, and release records agree; workspace checks and focused GPU/operator runs prove the actual paths; no stale evidence or hidden fallback remains. Never substitute a model-specific implementation, benchmark-only fast path, hardcoded shape table, consumer name, driver name in shared code, model crate, model graph builder, copied native kernel, mock execution, shape-only test, source-string test, fake route, edited benchmark fingerprint, or public API snapshot for the generic capability. Do not optimize one workload by bypassing Vyre.
